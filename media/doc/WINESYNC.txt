# ReactOS WINE porting/syncing reference file
# Update this file when you port/sync a dll/program from WINE.

The ReactOS Project shares quite a bit of code with the WINE project.
This document should provide a complete reference for all of the
locations in the ReactOS source tree where code is shared between the
two projects. If you find something is missing from this documentation
please add it.

If you find that a function in ReactOS that is not implemented properly
and is based on WINE sources, check the latest Winehq CVS and see if
it has been fixed there. If so, please submit a patch to
ros-dev@reactos.org. Otherwise please send a patch to both
wine-patches@winehq.com and ros-dev@reactos.org

Notes for syncers
-----------------

WIN32_NO_STATUS is not removable
    Wine removed "#define WIN32_NO_STATUS" from a number of modules between
    Wine-10.0 and Wine-11.18 (e.g. dlls/mcicda/mcicda.c,
    dlls/netutils/main.c). Do NOT carry that removal across.

    In ReactOS both sdk/include/psdk/ntstatus.h and sdk/include/xdk/winnt_old.h
    wrap their STATUS_* definitions in "#ifndef WIN32_NO_STATUS". The pattern
    used throughout our wine modules is therefore:

        #include "ntstatus.h"
        #define WIN32_NO_STATUS
        #include "windef.h"

    i.e. let ntstatus.h define the codes, then stop winnt.h from defining them
    a second time. Dropping the define makes both headers try to define the
    same macros. Wine can drop it because it builds against its own headers.

    When a component's ONLY upstream delta is that removal, there is nothing
    to take and the entry can simply be marked as synced.

WINE_NO_UNICODE_MACROS undef blocks are not removable
    Same class as WIN32_NO_STATUS. Several of our .idl files open with

        cpp_quote("#ifdef WINE_NO_UNICODE_MACROS")
        cpp_quote("#undef CopyFile")
        cpp_quote("#undef DeleteFile")
        cpp_quote("#undef MoveFile")
        cpp_quote("#endif")

    Wine removed that block from dlls/scrrun/scrrun.idl and others. Do not
    carry the removal here.

    Our sdk/include/psdk/winbase.h defines CopyFile, DeleteFile and MoveFile
    as A/W macros under #ifdef UNICODE AND under an #else for the ANSI case,
    so the identifiers are macros in both configurations. scrrun.idl declares
    methods actually named CopyFile, MoveFile and DeleteFile, so without the
    undef the generated proxy and stub code has those method names rewritten
    by the preprocessor. Wine can drop the block because its build defines
    WINE_NO_UNICODE_MACROS; ours only does so in
    modules/rostests/apitests/com.

Wine's tests/ directories are not synced here
    Upstream test suites live in modules/rostests/winetests in our tree, not
    next to the DLL. A component whose only upstream delta touches tests/ has
    no source change to take.

Deliberate reductions are not upstream bugs
    Some modules intentionally carry less than upstream, e.g.
    base/applications/cmdutils/reg has no REG_QWORD support. Upstream changes
    that live inside such a removed block cannot be applied and should not be
    silently re-added; keep the reduction and note it.

    A large enough reduction makes the whole file unmergeable, which is why
    dll/win32/wbemdisp/locator.c is deferred. Our copy is Wine's file about a
    thousand lines shorter: the ISWbemMethod, ISWbemMethodSet and
    ISWbemNamedValue/ISWbemNamedValueSet families are not there, and neither
    are the struct object internals they use. Wine 11 rewrites
    EnumVARIANT_create to serve all three enumerations from one function
    taking a new enum enum_variant_type - our copy still has the older
    IEnumWbemClassObject-only version - and adds ISWbemQualifierSet and
    ISWbemObjectPath implementations that build on the removed object model.
    A three-way merge gives 22 conflicts. Two of the rewrite's three callers
    are in the code we dropped, so a partial take is not worth attempting.

    The part that does not depend on any of that was taken on its own:
    main.c's factory_QueryInterface now clears *obj before returning
    E_NOINTERFACE. Check a reduced file for one or two separable hunks before
    deferring the whole component.

    A spec can carry the same kind of reduction. dll/win32/mscms exports
    WcsGetDefaultColorProfile, WcsGetDefaultColorProfileSize and
    WcsGetDefaultRenderingIntent as "@ stub" where Wine has had them as
    "@ stdcall" with implementations since well before 10.0. They are not
    part of the 11.18 delta, so they were left alone: taking them would mean
    importing three functions that no upstream change asks for. They are
    stubs in Wine too - each one only prints a FIXME and sets
    ERROR_CALL_NOT_IMPLEMENTED - so the difference is a slightly better
    message rather than behaviour. The file stays self-consistent, which is
    what matters: every "@ stdcall" line has a definition and no "@ stub"
    line has one. Re-check that invariant after editing any spec.

Picking hunks out of a forked file
    A file can be too far from Wine for a merge to be meaningful and still
    contain individual fixes worth having. wldap32 in 11.18 is the case: our
    copies are between 33% and 87% Wine lineage, and the full delta reports
    work in seven files, but three of the changes are self-contained and
    land in code we do have.

    misc.c's strnAtoW() wrote its terminator with *++d = 0 instead of
    *d = 0, one byte past the end of everything it had just written. page.c
    called ber_flatten() before checking whether ber_printf() had failed,
    and leaked the berval when the copy of it could not be allocated. option.c
    had LDAP_OPT_GETDSNAME_FLAGS and LDAP_OPT_PROMPT_CREDENTIALS in its
    "unsupported option" lists; Wine 11 implements both, so they were moved
    out of the lists and given the same stub bodies upstream uses. In all four
    cases our code was the same shape as upstream's, which is what made them
    separable - the check is whether the lines upstream changed exist in our
    file at all, not whether the file as a whole is close.

    Two of page.c's other fixes were skipped because our page.c has no
    search->cookie field for them to apply to, and bind.c's fixes were
    skipped for the same reason: our bind.c is a different implementation
    without the SASL default-credentials function they change. ld_host in
    winldap_private.h is PCHAR here and unused, so changing it to WCHAR would
    have no effect on its own.

    What is not ported is init.c's DC discovery. Wine 11 makes ldap_connect()
    call DsGetDcNameW() on the stored host and, on success, point the
    connection at the returned domain controller, which is why ld_host became
    a WCHAR * that is allocated in ldap_initW and freed in the two destroy
    paths. That is a feature with its own behaviour, not a fix: it changes
    which server a connection ends up talking to. ReactOS has dsgetdc.h,
    lmcons.h, lmapibuf.h and NetApiBufferFree, so it could be ported, but it
    should be done deliberately against our own host handling rather than
    merged out of a diff.

A shared psdk header can block a component sync
    Some Wine modules call proxy helpers that widl generates from a shared
    interface description in sdk/include/psdk. If the interface is not defined
    there, the generated helper does not exist and the upstream code cannot
    compile, however self-contained it looks.

    dll/win32/actxprxy was the first instance. Wine-11.18 adds
    IEnumObjects_Next_Proxy and IEnumObjects_Next_Stub to usrmarshal.c, but
    sdk/include/psdk/shobjidl.idl only forward-declared IEnumObjects inside a
    coclass - there was no "interface IEnumObjects : IUnknown" block, so
    IEnumObjects_RemoteNext_Proxy would never be generated and the type was
    incomplete. The hunk on its own would not build. Both were taken together:
    the interface block was added to our psdk idl verbatim from Wine-11.18,
    and usrmarshal.c followed. widl emits the *_Proxy and *_Stub prototypes
    for a [call_as] method into the interface header it generates, so defining
    the interface is all that is needed - there is no separate list of
    interfaces to register, and actxprxy.spec exports no _Proxy or _Stub
    names.

    Take the header change first, or leave the component where it is. The same
    trap applies to any hand-written *_Proxy/_Stub in a *marshal.c file:
    check that the interface is defined in the psdk header the module includes.

    A second form of the same trap: upstream adds the implementation and the
    type it needs in the same release. dll/win32/pdh gained real
    PdhGetFormattedCounterArrayA/W and PdhGetRawCounterArrayA/W and a
    PdhEnumObjectsA/W export, and Wine 11 added PDH_FMT_COUNTERVALUE_ITEM_A/W
    and PDH_RAW_COUNTER_ITEM_A/W to include/pdh.h to go with them. Our
    psdk/pdh.h did not have those types, so the sources alone would not
    compile. The header was updated in the same commit here.

    Note that our pdh.h has dropped Wine's DECL_PDH_TYPE_AW macro, so add the
    plain _A/_W structs and keep WINELIB_NAME_AW for the generic names.

    bluetoothapis is the largest instance so far, and it is deferred rather
    than attempted. Wine 11 turns the BluetoothFindFirstDevice,
    BluetoothFindNextDevice, BluetoothFindDeviceClose, BluetoothGetDeviceInfo,
    BluetoothGetRadioInfo, BluetoothIsConnectable, BluetoothEnableDiscovery,
    BluetoothEnableIncomingConnections, BluetoothAuthenticateDeviceEx,
    BluetoothRegisterForAuthenticationEx and BluetoothSendAuthenticationResponseEx
    stubs into real implementations, adds gatt.c with the BluetoothGATT
    entry points, and adds a resource for the pairing wizard's strings. Four
    headers it needs do not exist here at all: bthledef.h, bthioctl.h,
    bluetoothleapis.h and wine/winebth.h. bluetoothapis.h itself is missing
    BLUETOOTH_PIN_INFO, BLUETOOTH_OOB_DATA_INFO,
    BLUETOOTH_NUMERIC_COMPARISON_INFO, BLUETOOTH_PASSKEY_INFO,
    BLUETOOTH_AUTHENTICATE_RESPONSE, BTH_MAX_PIN_SIZE and two prototypes,
    and the authentication path also wants CM_Register_Notification and
    friends from cfgmgr32.h. Wine's cfgmgr32.h delta for those is 392 lines
    and cannot be pasted in: our cfgmgr32.h is 3224 lines of ReactOS's own
    and already defines CM_GETIDLIST_FILTER_NONE, LOG_CONF,
    CM_OPEN_CLASS_KEY_INSTALLER and CR_SUCCESS, so the additions would have
    to be applied selectively by hand, without a compiler to check them.
    The new code also talks to Wine's bluetooth driver through the IOCTLs in
    winebth.h, which ReactOS's own bluetooth stack does not implement.

    There is no separable part to take: every removed line in main.c is a
    stub the new code replaces. Check that before deferring, as the wbemdisp
    entry above describes.

The ledger can understate what is already synced
    A component whose entry says Wine-10.0 may already carry an upstream
    change, because ReactOS fixed the same bug independently. dll/win32/mciavi32
    is the example: its entry said Wine-11.11 and its mmoutput.c already
    matched Wine-11.18 except for two __REACTOS__ blocks, so the frame
    clamping and the TRACE that upstream added were already present. A
    three-way merge against the 10.0 baseline then reports conflicts on lines
    that are in fact identical on both sides.

    When a merge conflicts, check the file against wine-11.18 before resolving
    anything. If the only differences are __REACTOS__ blocks, the component is
    already synced and there is nothing to take.

Check that a file is actually Wine's before merging into it
    A ledger entry names a path, but the code under that path is not
    necessarily Wine's. Some components took only Wine's .rc and .spec and
    keep a ReactOS implementation of the code; some programs were forked long
    ago. A three-way merge against a Wine baseline happily "applies" hunks
    from a different program and produces nonsense.

    Measured against Wine-11.18, these are NOT mergeable:

        dll/win32/version/version.c     ~20% shared with Wine's version.c
        base/applications/notepad       ~29% shared; forked at Wine-20041201
        dll/win32/mpr/mpr.rc            ~24% shared; our file is the
                                        language-include layout

    whereas dll/win32/mpr/wnet.c (89%), base/applications/wordpad (92%) and
    the odbccp32/cryptnet/cryptui sources (99-100%) are Wine's code and merge
    normally. Diff the file against the Wine baseline and look at how much is
    unchanged before trusting a merge.

A new resource file is not automatically worth taking
    Wine 11 added dlls/mscms/rsrc.rc, which is one line of resource script
    bundling an srgb2014.icc data blob as resource 1. Nothing in Wine's own C
    code reads it - the whole tree references that file only from the .rc
    itself - so it looks like groundwork for a later release. It was not
    taken. Our resource compiler has no WINE_DATA_FILE macro, which is what
    the line uses, and we do not carry the .icc, so the file would not even
    build until an rc header and the blob were added too, for no consumer.

    When a new upstream file is a resource, check whether any source file
    references what it defines before adding it.

Wine moved version resources into its Makefiles
    From Wine 11 onwards, version information often no longer lives in the
    module's .rc file. It moved to the Makefile as

        VER_PRODUCTVERSION = 5,1,2600,2180

    which Wine's own makedep turns into a generated resource, and the .rc file
    was deleted upstream. ReactOS's CMake build has no equivalent mechanism,
    and our .rc files are named explicitly in CMakeLists.txt, so the deletion
    is not something to follow: keep the local .rc.

    A component whose only upstream delta is such a deletion has nothing to
    take and can be marked as synced. As of Wine-11.18 that applies to
    comcat, lz32, mciqtz32, mspatcha, objsel, olepro32, olethk32, rsabase,
    shfolder, stdole2.tlb, stdole32.tlb, version and others. Check whether the
    deleted .rc still exists locally and is referenced by CMakeLists.txt
    before concluding anything.

    The same reasoning covers a deleted .rc we have no counterpart for at all:
    nothing to do.

A spec is only mergeable if the ordinals still line up
    uxtheme is the clearest case. Wine 11 adds four Immersive colour
    functions to system.c and the matching spec entries, but our
    uxtheme.spec is not Wine's: it is 29% Wine lineage and reordered, so
    our ordinal 49 is GetThemeAppProperties while Wine's 49 is "stub @".
    Taking upstream's spec hunk would collide with an existing export.

    powrprof is the milder version of the same problem. There are no explicit
    ordinals in either spec - they come from the order of the lines - and our
    spec is sorted alphabetically while Wine's is in historical order.
    Wine 11 adds PowerRegisterForEffectivePowerModeNotifications, which we do
    not have, and PowerReadACValueIndex, which we have had for years:
    our powrprof.c is ReactOS's own (12% Wine lineage) and already exports
    PowerReadACValue, PowerReadACValueIndex, PowerReadDCValueIndex and
    PowerWriteDCValueIndex. Inserting Wine's two lines mid-file would
    renumber every export after them, so the only export worth taking is one
    that needs a new function written, not an upstream hunk merged.

    The component also keeps two spec files, uxtheme.spec and
    uxtheme_vista.spec, chosen by DLL_EXPORT_VERSION in CMakeLists.txt, and
    the vista one is where the newer ordinals live (uxtheme_vista.spec:102
    is already "102 stub GetThemeStream"). Adding an export correctly means
    deciding which file it belongs in and which ordinal is free, not
    applying a diff.

    On top of that, GetImmersiveColorFromColorSetEx calls
    ShouldAppsUseDarkMode, which Wine has had since well before 10.0 but
    our uxtheme does not implement at all, so the Immersive block cannot
    come across on its own.

    The draw.c part is separable and small - a null-options fix in
    DrawThemeTextEx, the parentless-window early return, and two new
    stubs - and is worth doing as its own change with the ordinal work.

Upstream deletions are not automatically ours
    Wine 11 deletes DllGetVersion and URLSubRegQueryA from
    dlls/shdocvw/shdocvw_main.c, having moved their functionality
    elsewhere. Our shdocvw.spec still exports both - DllGetVersion at
    "@ stdcall -private" and URLSubRegQueryA at 151 - and we implement
    them, so following the deletion would leave two dangling exports. Keep
    them, as with WIN32_NO_STATUS.

    .spec and .rc came from Wine. Upstream deltas to those cannot be merged;
    they would have to be reimplemented. Measured against Wine-11.18:

      dll/win32/xinput1_3, xinput9_1_0   ours are older from-scratch

A spec's parameter list does not change the built binary
    It is natural to worry when upstream rewrites a .spec parameter list,
    e.g. imagehlp.spec changing several -import entries from (long long) to
    (long ptr) between Wine 10.0 and 11.18. In ReactOS those changes are
    cosmetic:

      - sdk/tools/spec2def/spec2def.c writes the stdcall suffix from
        pexp->nStackBytes only when giArch == ARCH_X86; for every other
        architecture it prints the undecorated name and never looks at the
        argument sizes.
      - On i386 long and ptr are both 4 bytes, so nStackBytes is unchanged
        and the decoration is identical either way.

    So a spec parameter list cannot introduce an argument-size mismatch, and
    taking upstream's is safe. It also does not have to agree with the
    signature our own dbghelp.spec lists for the same forwarded function,
    though there is no harm in aligning them.

Wordpad keeps its own window placement
    Wine-11.18 replaces wordpad's manual MonitorFromRect/IntersectRect
    clamping with a WINDOWPLACEMENT and SetWindowPlacement in WinMain. Ours
    uses ReactOS's class and title strings and its own rect handling, so only
    the SW_SHOW/SW_HIDE changes were taken; the placement rework was left
    out.
